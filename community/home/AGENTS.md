# 全局开发规则

## 适用范围

- 全局所有项目生效。
- **新代码必须遵守**本文件规则。
- **存量代码逐步治理**：存量超限不阻断审查，只提示用户，不擅自大规模重构。

---

## 1. 代码架构硬性指标

### 文件行数

- 动态语言（Python、JavaScript、TypeScript）：单文件不超过 200 行。
- 静态语言（Java、Go、Rust）：单文件不超过 250 行。

### 文件夹结构

- 每个文件夹内文件数量不超过 8 个，根目录除外。
- 超过 8 个文件时，需拆分为多层子文件夹。

### 存量代码

- 存量文件或文件夹超限时，只提醒逐步治理，不阻断代码审查，不擅自拆分。

## 2. 架构设计关注点

以下坏味道必须持续警惕；发现时应提醒用户并给出优化建议，不擅自大改：

- 僵化：微小改动引发连锁反应。建议接口抽象、策略模式、依赖倒置。
- 冗余：相同逻辑重复出现。建议提取公共函数或类，用组合代替继承。
- 循环依赖：模块相互依赖形成死结。建议接口解耦、事件机制、依赖注入。
- 脆弱性：修改一处导致无关部分出错。建议遵循单一职责，提高模块内聚。
- 晦涩性：结构混乱、意图不明。建议清晰命名、必要注释、简洁结构、完善文档。
- 数据泥团：多个参数总是一起出现。建议封装为数据结构或值对象。
- 不必要复杂性：过度设计。建议遵循 YAGNI 和 KISS 原则，按需设计。

## 3. 中文开发规范与偏好

### 对话与文档

- 对话、解释、文档默认使用中文。
- 错误信息和调试信息使用中文描述。
- 用户界面文本使用中文，支持国际化预留。
- Git commit 信息使用中文描述功能变更。

### 代码命名

- 变量名、函数名、类名使用英文，遵循 JavaScript/TypeScript 规范。
- 文件名使用英文，采用 PascalCase 或 camelCase。
- 常量使用 UPPER_SNAKE_CASE 英文命名。
- 类型定义使用英文，接口名以 I 开头。

### 注释

- 所有导出的函数和类必须有中文 JSDoc 注释。
- 复杂业务逻辑必须有行内中文注释。
- 工具函数需要中文说明参数和返回值。
- React 组件需要中文注释说明用途和 props。

注释格式示例：

```typescript
/**
 * 画布工具管理器 - 负责工具切换和状态管理
 * @param toolType 工具类型
 * @returns 工具实例
 */
```

### 开发标记

- TODO：中文描述待完成功能。
- FIXME：中文描述需要修复的问题。
- NOTE：中文添加重要说明。
- HACK：中文说明临时解决方案。

### 用户界面文本

- 按钮文字、菜单项使用简洁中文。
- 错误提示使用友好的中文表达。
- 工具提示使用中文说明。
- 状态信息使用中文反馈。

### 数值和单位

- 尺寸单位使用“像素”而非“px”。
- 百分比使用“百分之”或“%”。
- 时间单位使用“秒”、“毫秒”等中文。

### 开发流程

- 代码审查评论使用中文。
- 变更说明使用中文描述影响范围。
- 技术决策文档使用中文记录。
- console.log 调试信息使用中文。
- 错误日志使用中文描述问题。
- 性能监控标记使用中文标识。

### 文档

- API 文档使用中文描述功能。
- 架构文档使用中文解释设计思路。
- 部署文档使用中文说明步骤。
- 用户手册使用简洁中文。
- 功能说明使用通俗易懂的中文。
- 常见问题使用中文问答格式。

## 4. 开发环境与执行规范

### 环境

- 开发电脑系统为 Windows，终端使用 Windows PowerShell。

### 方案与计划

- 存在多个实施方案时，选择最符合项目功能实现的方案。
- 每次提供计划时，必须进行清晰的分步规划。
- 计划确认后严格执行，不得重复执行已成功完成的步骤；失败重试、格式化和构建验证迭代不在此限。
- 计划执行完整后确有遗漏时，再提出补充；执行过程中不要中途增加无关改动。

### 代码真实性

- 严禁生成虚假代码、模拟代码或占位实现。
- 所有生成的代码必须确保可以实际运行。

### 通用功能选库

- 通用功能必须优先使用成熟库。
- 引入成熟库前必须评估并同时满足：
  - GitHub Stars > 1000。
  - 近一年内有更新。
  - 许可证与项目兼容。
- 例外：项目已有依赖或用户指定的库，可不受 Stars 和更新时间条件限制。

### 日志记录

- 每次修改完成后，记录修改内容概述。
- 严禁将具体实现和方案写入日志。
- 严禁覆盖当天已记录的日志；可以整理当天已记录的日志。
- 日志文件以当天真实日期命名。
- 日志放在当前项目根目录的 `logs` 文件夹中；不存在时可以创建。
- 未经用户同意，不得创建其他日志文件。

### 新对话上下文

- 每次开启新对话时，自动检索项目架构和实现。

### 前端页面设计

- 所有涉及前端页面设计的实现，均不允许使用 emoji 表情图标和文本表情图标。

### GitHub 操作

- 严禁自动安装 GitHub CLI。
- Git 提交、推送仍使用 Git；PR、Issue、Release 等 GitHub 平台操作使用 API 方式。
- GitHub API 认证：优先使用本机已配置的 `gh api` 调用 GitHub REST API；它复用本地 GitHub OAuth，不要求当前 Codex 会话存在 `GITHUB_TOKEN` 或 `GH_TOKEN`。严禁自动安装 `gh`，也不得读取、输出、记录或提交原始令牌。
- 创建 PR：先确认分支已推送，再通过 `gh api` 创建或查询目标 PR；必须回查 PR 的正式 `html_url` 后再向用户交付，不能只提供新建页或比较页链接。
- `gh` 不可用时：必须尝试本机 Git 凭据管理器的 GitHub 凭据作为 REST API 回退路径。仅允许在单个进程内通过 `git credential fill` 获取 `https://github.com` 凭据并立即用于 `curl`/PowerShell REST 请求；令牌只能留在进程内存，严禁输出、写入文件、写入日志、提交或在回复中展示。不能因为缺少 `gh`、Netrc 或环境变量就直接放弃创建 PR。
- REST API 创建 PR 流程：先用同一凭据查询 `head + base` 是否已有开放 PR；没有则 `POST /repos/{owner}/{repo}/pulls` 创建；随后 `GET /repos/{owner}/{repo}/pulls/{number}` 回查 `html_url`、`head.ref`、`base.ref` 和状态。只有这些字段确认正确后才能向用户交付正式链接。
- 填写 PR 描述时使用 UTF-8 编码。
- PR 完成后提供正式 PR 链接。
