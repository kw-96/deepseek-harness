# Agent Note: 桌面壳看护 `dsh web` 后端并在其退出后自动重启

Status: implemented

[English](2026-09-11-desktop-shell-backend-watchdog.md) | 中文

## Problem

桌面壳把窗口导航到 `dsh web` 的地址之后就不再理会这个子进程。后端掉线时窗口本身不会失效——前端的重连循环会一直显示「自动重连中…」——但没有任何环节把它拉起来，只能手动在仓库根目录重新执行 `dsh web`。手动拉起的进程不属于壳：关闭窗口时它不会被结束，会继续占着端口，下一次双击就直接撞上端口占用。

两处相邻缺陷让这条路径更难用、也更危险：

- 就绪等待用阻塞迭代读取子进程输出，超时只在「下一条输出到达」之后才被检查；`dsh web` 卡住且不再输出时，180 秒超时永不触发。
- 结束子进程树之前不检查它是否已经退出。子进程自行退出后 pid 可能已被系统复用，`taskkill /F /T /PID` 会误杀无关进程树。

## Decision

把子进程生命周期从 `lib.rs` 拆成 `child` 与 `backend` 两个模块，`lib.rs` 只留应用装配与窗口事件。

- `child` 拥有子进程：启动、结束、退出查询。`kill_tree` 先用 `try_wait` 确认它仍在运行，才按 pid 结束进程树。
- `backend::run_backend` 循环负责启动与看护：启动、等就绪、首次导航、排空输出直到子进程退出、等 3 秒后重启。就绪等待与退出监视都改用 `recv_timeout` 轮询，超时与退出判定都不再依赖「还有输出到达」。
- 重启不再导航。窗口里的前端持有持久密钥签发的认证 cookie，会自行重连；进程级 launch token 每次都变，但重连不需要它。
- 连续 3 次启动失败（例如端口被另一个实例占用）返回错误，由调用方按打开配置失败处理，不再无限重启。

## Alternatives considered

**重启后重新导航。** 否决：整页重载会丢掉页面内状态（面板、草稿、滚动位置），而客户端本来就能重连。

**只报错不重启，把掉线交给用户。** 否决：这正是本次要修的体验——窗口会一直停在重连提示上。

**启动时探测端口上已有实例并直接接管。** 否决：无法确认那个实例属于同一个 Harness home 与 profile，接管错实例比报错更糟。

## Consequences

后端掉线约 3 秒后被自动拉起，窗口自行重连，无需关闭窗口或手工重启。启动失败仍然响亮地失败：诊断文本（退出状态加输出末尾的 `Error:` 行）保持不变。壳仍只导航一次，因此若前端的重连循环放弃重试，窗口不会自动恢复。

原生部分需要重建壳才生效（`pnpm --filter @deepseek-ai/dsh-experimental-web-desktop build`）。该脚本在旧壳仍占用根目录 `DeepSeek Harness.exe` 时改为把它改名备份到 `.data/` 再写入新产物，因此换代不再需要先关闭正在运行的窗口。
