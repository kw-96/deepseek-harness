# Agent Note: 可省 Remote 参数被省略时的解析

Status: implemented

[English](2026-09-12-omissible-remote-argument-parsing.md) | 中文

## Problem

严格描述符可以用 `acceptsUndefined: true` 声明某个 JSON 参数可省。宿主侧在检查到达的 `args` 对象时遵守该声明：声明可省的参数允许字段缺失（`assertExactArguments`）。客户端侧没有遵守。它准备的调用会解析**每一个**声明过的参数，包括调用方根本没传的那个，于是缺失值被送进了只描述「值存在时」形态的编解码器。

两半边因此对同一份描述符的理解不一致。`limit` 这种参数的编解码器写成朴素的 `z.number()`——表达「有值时为数字」最自然的方式——时，浏览器只有传值才能调用成功；不传就会在请求离开进程之前得到 `client api: <endpoint> rejected "<parameter>"`。这个失败表现为面板坏掉，而不是一条点名真正分歧的诊断，因为编解码器的拒绝被包装成了客户端内部故障。

这个缺口一直没被发现，是因为唯一覆盖 `acceptsUndefined` 的夹具把编解码器写成了 `z.union([z.string(), z.null(), z.undefined()])`。该夹具通过的原因与被测机制无关：它在 schema 层就接受了缺失值，因此根本走不到「客户端是否解析」这个分支。

## Decision

客户端准备的调用在调用方未传值时跳过声明可省的参数，而不是解析它。该参数不出现在线上 `args` 里；宿主只对真正到达的值应用编解码器，缺失值意味着什么由操作自身的默认逻辑决定。

声明可省的参数，其编解码器只描述「值存在时」的形态。它无需在 schema 层接纳 `undefined`，因此只声明 `acceptsUndefined` 而不放宽 schema 的描述符是合法的，不是陷阱。

实参个数不变：调用方仍需为每个声明过的参数提供一个位置值，想省略的那个传 `undefined`（`log(cwd, undefined)`）。完全省掉末尾位置仍是元数错误，因为参数按位置对应，更短的列表无法表达省略的是哪一个。

## Consequences

面板现在可以不写可省参数就调用 Remote 方法，并由宿主侧的默认值生效——这正是描述符一直以来的承诺。插件侧那种把编解码器放宽成 `z.number().optional()` 的绕法不再是为了让调用能够送达，尽管接纳 `undefined` 的 schema 仍然无害。

失败形态是转移而非消失：客户端传错类型仍在解析期失败，传的位置值过少仍在元数检查处失败。只有「缺失值」这一种情形改变了归属。

备选参数选择不受影响。lookup 参数由调用方的 Context 解析而非位置值，因此它在可省检查之前就被跳过，行为保持原样。

回归夹具用朴素的 `z.number()` 声明 `limit`，因此它固定的是机制本身而不是 schema 的宽容度：一旦客户端重新解析缺失值，它就会失败。

## Alternatives considered

**把所有可省参数的编解码器放宽到接纳 `undefined`。** 这正是已发布夹具的做法，而且它有效——`z.number().optional()` 能解析缺失值，随后既有的 `value !== undefined` 判断会略过该字段。它被否决，是因为这要求每份描述符复述一条描述符本身已经声明的规则：`acceptsUndefined` 在编解码器层将失去意义，而真正的约束落在编解码器上；任何写下自然写法 `z.number()` 的作者都会撞上同一个被包装过的失败。它还让网关两半继续各执一词，下一位读者必须重新弄清哪半边在强制什么。

**放宽元数检查以接受更短的位置列表。** 它被否决，因为对于拥有多个可省参数的描述符，更短的列表是有歧义的；而且这项检查正是防止「忘了传的实参被静默当作使用默认值」的那道闸。显式的 `undefined` 占位让调用方的意图在调用点可见。

**把缺失的可省值当作错误。** 它被否决，因为这与宿主的行为矛盾——宿主已经接受该字段缺失；而且这会让 `acceptsUndefined` 变成只有宿主侧有意义、在客户端毫无含义的声明。
