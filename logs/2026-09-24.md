## 第三方插件排查与 dsh-github 生态纳入（用户要求）

- 处置：按用户要求把上游 `kaziii/dsh-github-connector` 的五个包（能力缝、REST provider、模型工具、Device Flow 连接、工作流界面）克隆进 `community/plugins/packages/` 做二次开发适配——peer 与依赖对齐当前版本线、补齐构建脚本、修掉 0.1.7 中已移除或改名的 API 差异。原仓库的构建链（入口 shim + 客户端打包）替换为本仓社区插件的既有约定。
- 连带：community 插件清单（中英双语与配对哈希记录）补入五个新包；分发包归档至 `tarballs/`。模块版本不一致导致的类型错误按「依赖对齐」而非「放宽类型」处理。
- 验证：五个包编译零错误，产物结构符合客户端模块加载器与 bundle 声明要求；按 app-boot 兼容性规则对 desktop profile 全部 bundle 逐个判定，12 项全部放行。desktop profile 已装入该生态（含把落后的 browser-skill 升到 npm 最新），待用户重启生效。

## 桌面壳下第三方插件的三处兼容缺口（无仓库代码改动，就地补丁）

- 背景：0.1.7 桌面壳里另有三个第三方插件界面失效，根因都在插件自身对 0.1.7 / 桌面壳的假设，与本仓代码无关，因此**没有仓库侧改动**，补丁只落在 profile 的 `node_modules` 里；本节记录以备其他机器复现。
- 缺口一（mnemon 设置页控件全部禁用、且控制台不报错）：桌面壳加载页面的来源是自定义协议 `dsh-app://…`，页面主机名既非 `localhost` 也非回环地址；插件按主机名判定「是否远程页面」时把桌面壳的本地页面误判成配对的手机端页面，请求改走功能被裁剪的通道，控件可用性字段缺失，于是整页禁用。判据改为按协议识别桌面壳本地页面后恢复。**上游 `dsh-mnemon` 0.5.13（当前最新）仍如此。**
- 缺口二（remote-mobile 设置注入失效，插件停在 pending）：客户端仍声明 0.1.7 已改名的设置服务名；该服务在该插件里实际未被使用，属声明残留，改掉声明即恢复。**上游 `dsh-remote-mobile` 1.7.0（当前最新）仍如此。**
- 缺口三（mnemon 偶发的设置首读失败）：插件构造后立即读取设置，而 0.1.7 的客户端传输是异步建立的；首读落在就绪之前会静默降级且不再重试。已补连接代际重试，实测并非前两项故障的原因，作为防御保留。
- 处置与复现：以上均为就地补丁，改动内容、原文件备份名与重放步骤记录在 `~/.dsh/profiles/desktop/LOCAL-PLUGIN-PATCHES.md`；**升级这三个包会覆盖补丁，需按该文件重新应用**。另有一条 host 侧 RPC 调用追踪属排查诊断，用完可整段删除。
- 影响范围与其他机器：任何使用桌面壳（`profile=desktop`）并安装上述插件的机器都会遇到同样现象，照该文件重放即可；本仓 `dev` 不含也不需要相关代码改动（`packages/client/connection` 的 `webServer` 取服务修复属仓库代码，已随 0.1.7 底座合入 `dev`）。
