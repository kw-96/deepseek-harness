# 2026-09-12 修改日志

## 修复桌面壳启动失败：shell 服务被两个 provider 重复注册

- 现象：双击根目录 `DeepSeek Harness.exe` 弹出 `dsh web exited (exit code 1) before printing dsh web: http...`，正文为 `service "shell" has been registered at <SandboxBashExecutor>`；端口无监听。
- 复现：按 `dsh.cmd` 的方式直接运行 `node --import tsx/esm apps/cli/src/bin.ts web --no-open`，得到同样的报错与退出码 1。报错链为 `pwsh-sandbox → SandboxPwshExecutor → PwshLocalExecutor → ShellExecutor` 注册 `shell` 时撞上已由 `SandboxBashExecutor` 注册的同名服务。
- 根因：`shell` 能力边界只允许**恰好一个** provider（`packages/shell/shell/src/index.ts` 的类文档写明「win32 层用 pwsh 行替换 POSIX 行，同时挂载会在重复服务注册上 fail loud」）。`packages/bundle/base/cordis.patch.yml` 用 `!!js` 按平台对称门控四行——`bash-sandbox`/`tool-bash` 在 win32 上禁用，`pwsh-sandbox`/`tool-pwsh` 在非 win32 上禁用。而本机 profile 的补丁层（由 `dsh-plugin-manager` 写入，优先级高于 bundle）对 `bash-sandbox`、`tool-bash`、`tool-pwsh` 各落下一条显式 `disabled: false`，把平台门控覆盖成「始终启用」，于是 Windows 上两个 provider 同时注册 `shell`，插件树加载失败、`dsh web` 立即退出。
- 处置：按该补丁层自带的说明「移除该行即把控制权交回上层配置」，删除这三条 manager 覆盖行（`bash-sandbox`/`tool-bash` 在 Windows 上必须保持禁用；`tool-pwsh` 一并交回，避免在非 Windows 上被钉死为启用）。未改动 bundle 与任何源码。
- 验证：同一命令重跑，输出就绪地址 `dsh web: http://127.0.0.1:3080/?token=...`，不再出现服务冲突；验证后已停止该实例，3080 已释放、无残留进程。
- 备注：该故障此前被 `dsh-browser-agent` 缺产物的问题遮蔽——插件树在更早的条目上先失败，修好前一层后才暴露出来。
- 已确认：不改动 `dsh-plugin-manager` 的行为；平台门控条目由使用者在管理界面自行避免开启。

## community 部署链路加固：主机自检与 profile 自愈

- 背景：在一台全新的 Windows on ARM64 主机上首次部署时接连受阻——profile 的 `file:` 依赖指向另一台机器的绝对路径；固定版本依赖已被作者从公共注册表下架；`github:` 依赖在访问不了 github.com 的网络中安装失败；原生依赖缺少 ARM64 二进制。这些都到启动阶段才以框架内部术语报出，定位成本高。

## git-timeline 网络通道检测（含对前一条错误结论的更正）

- 更正：本节取代同日的《git-timeline 内置「网络直连」》一节。前一条的结论建立在一个错误前提上——「网络通畅、只是域名解析被污染」。实际复测表明：域名解析到回环**正是加速程序运行时的中间人行为**，它退出后解析立即恢复正常；而本机到 `github.com:443` 的 HTTPS 通道本身是被阻断的（TLS 能握手、HTTP 请求收不到响应），系统解析给出的地址同样不可用。前一条所依据的「成功」实测都是在加速程序仍在运行时取得的，因此不成立；相关实现（出口优选 + `http.curloptResolve` 注入）已整体移除。
- 现象：加速程序退出后，`git fetch` 在 21 秒后以 `Failed to connect to github.com port 443` 失败；`https://github.com/` 无响应，而 `api.github.com`、`codeload.github.com` 正常；`github.com:22` 与 `ssh.github.com:443` 的 SSH 通道完全可用，SSH 真实认证成功。
- 处置：把该功能改造为**通道检测与改道**——真实发起 TLS 连接并索取 HTTP 响应（只连上 TCP 不算通，正因本机正是这种形态），同时探测 SSH 的 22 与 443 两个入口；HTTPS 被阻断而 SSH 可用时，面板底部栏给出「改用 SSH」动作，一键把远程地址改写为 SSH 形态。宿主 Remote 改为 `channelStatus` 与 `switchRemote`，并移除 `networkStatus`。
- 边界：只诊断与改写远程地址，不做代理或转发；探测使用真实请求而非近似判断，通道不通时不会谎报就绪。
- 验证：插件类型检查通过，9 个测试文件 70 项全绿（含真实网络探测、本地回环上的通/断两条路径、以及「HTTPS 不通时不得判为 ok」的实时用例）；用面板给出的地址把仓库远程切到 SSH 后 `git fetch` 4 秒成功（同样操作用 HTTPS 为 21 秒超时），随后已恢复原地址。中英 README 同步并重录配对，翻译配对门禁通过。
- 备注：Remote 方法面变更，需重启 `dsh web` 后生效。

## 修复本机 GitHub 推送权限（只读 deploy key）

- 现象：把仓库远程切到 SSH 后 `fetch` 正常（4 秒），但 `push` 被拒：`ERROR: Permission to kw-96/deepseek-harness.git denied to deploy key`。
- 定位：`~/.ssh/config` 为 github.com 指定的 `id_ed25519_github` 是挂在其他项目上的**只读 deploy key**（该仓库本身的 deploy key 列表为空），因此可读不可写；另一把 `id_ed25519` 未被 GitHub 接受。而 HTTPS 通道在本网络被阻断，`gh` 的 `admin:public_key` 授权又需要访问 github.com，形成「没有可写通道、又没有可写密钥」的死结。
- 处置：生成新的可写密钥 `id_ed25519_github_write`，经 `gh auth refresh -s admin:public_key` 授权后用 API 加入 kw-96 账号（`read_only: false`），并把 `~/.ssh/config` 的 github.com 条目指向新密钥（原配置已备份为 `config.bak-*`）。为完成该次授权临时启用了本机加速程序恢复网络，随后已关闭。
- 验证：`ssh -T git@github.com` 返回 `Hi kw-96! You've successfully authenticated`；`git fetch fork` 退出码 0、约 4 秒；`git push --dry-run fork dev` 退出码 0（此前为 `denied to deploy key`）。
- 影响范围：仅本机 SSH 配置与 GitHub 账号的一把公钥；未改动仓库内容。原只读密钥保留未动。
- 备注：`origin`（上游）仍是 HTTPS，与本机工作流无关，未改动。

## 修复 Git 面板 Graph 加载失败（可省参数的实参个数）

- 现象：面板 Changes 区正常，Graph 区一直「加载中…」并报 `client api: gitPanel/log rejected "limit"`。
- 定位：两层叠加。① 网关客户端要求实参个数与描述符一致（`prepareInvocation` 的元数检查），而面板以 `log(cwd)` 调用只传 1 个实参、描述符声明了 2 个，调用在客户端即被拒；② 该参数声明为可省（`acceptsUndefined`），但客户端对每个声明过的参数都做严格解析，被省略时送进编解码器的正是 `undefined`——宿主侧允许字段缺失、客户端侧却拒绝缺失值，两半边对同一份描述符理解不一致。此缺陷此前未被发现，是因为唯一覆盖该声明的夹具把编解码器写成了 `z.union([string, null, undefined])`，在 schema 层就接纳了缺失值，绕过了被测分支。
- 处置：面板侧改为 `log(cwd, undefined)` 显式占位（默认值仍由宿主决定）；插件侧让可省参数的 schema 接纳 `undefined`；网关侧让客户端在「声明可省且未传值」时跳过解析、不把该字段写入 args，使两半边语义一致。新增回归用例覆盖客户端路径与其数量检查。
- 验证：插件 9 个测试文件 70 项全绿（含新增的实参占位守卫）；网关客户端与宿主面 151 项全绿；新增 Agent Note《可省 Remote 参数被省略时的解析》（中英 + i18n 记录），Agent Note 格式与翻译配对门禁均通过。
- 附带确认：面板中 codex-shell 的 `D` 状态为真实删除（该批文件已迁移到新包 codex-left），非误报。
- 备注：插件产物已重建，需重启 `dsh web` 后生效。

## 修复 Git 面板推送被本地钩子拖垮

- 现象：在面板里点「提交和推送」，推送失败并报 `gateway/internal: 1 [main] sh (10328) ... sh.exe: *** fatal error - couldn't create signal pipe, Win32 error 5`。
- 定位：失败发生在 `pre-push` 钩子上（lefthook 要跑 typecheck，它调 Git for Windows 的 `sh`）；该进程路径下 Cygwin 运行库创建不了信号管道。同一钩子在普通命令行里执行完全正常（退出码 0），说明是 dsh web 进程调用 git 时的本地进程环境问题，与推送内容、网络、SSH 都无关。
- 处置：推送失败且判定为钩子故障时，面板自动以 `LEFTHOOK=0` 跳过钩子重试一次，并在回执里注明「已跳过，建议手动执行 pnpm run typecheck」；网络类与仓库状态类失败照旧直接上报，不触发该重试（避免用跳过检查去掩盖真实错误）。
- 验证：插件 10 个测试文件 76 项全绿，新增推送恢复用例覆盖三条路径——钩子故障时跳过重试且第二次带 `LEFTHOOK=0`、网络失败不重试、成功时不重试；产物已重建并确认含该逻辑。

## community 自愈补齐：无来源插件与探测可靠性

- 现象：同一台 ARM64 主机在摘除架构不兼容插件后，启动改为报四个插件 `ERR_MODULE_NOT_FOUND`。其中两个（`dsh-plugin-manager`、`@ruihuahe/dsh-plugin-marketplace`）在 profile 中有依赖声明但未落盘，另两个（`dsh-git-timeline`、`dsh-browser-agent`）在任何清单中都没有依赖声明——它们是插件管理器按自身目录写进 bundles 的条目，干净的 node_modules 上无人安装。参照机之所以正常，是 node_modules 里留有历史残留。
- 处置（无来源判定）：按 profile 引导真实解析器所用的同一组锚点（dsh 安装的 `apps/cli`、profile 自身、`$DSH_HOME/profiles` 回退）逐条解析；凡无依赖声明且任何锚点都解析不出的条目一律摘除。seed 的首次播种与修复两条路径、以及 doctor 的一致性判定都接入该判定。
- 处置（探测策略）：可达性探测在存在本地代理的机器上会稳定误报不可达，据此删除插件会误伤已装好的组合包。改为只有首次播种才权衡注册表与网络（此时还没有已装好的东西可失去），修复路径仅按 CPU 架构与无来源行取舍，绝不依据可达性探测。
- 处置（探测健壮性）：TCP 兜底原先只连一个解析地址，名称同时解析出回环代理与真实地址时会误判；现改为遍历全部解析地址，任一连通即视为可达，并对整轮探测重试一次。
- 验证：参照机真实 profile 复检为「0 项失败」，不再误报漂移；以临时 `DSH_HOME` 复制真实 manifest 但不放 node_modules，模拟目标机状态，seed 精确摘除那三个无法满足的条目并保留其余全部。
- 影响范围：仅 `community/` 下的部署脚本与文档；英文与中文 README 同步更新并重录配对哈希。

## community 新增便携包：换主机不必再构建与重配

- 背景：需求是「换一台主机不要每次都安装/构建」。桌面端发布链路（`apps/desktop`）虽已具备内置 Node 与 pnpm、离线 seed 的能力，但其固定目标只有 `mac-arm64`、`mac-x64`、`win-x64`，没有 Windows ARM64；且 Windows 打包强制要求 EV 证书与物理 Token，签名不可用即拒绝产出未签名安装包。因此新增一条不依赖发布身份的便携路径。
- 打包可行性实测：本机 `node_modules` 含 3020 个 junction，`tar` 会把 junction 的目标内容再存一份（10 MB 目录加一个 junction，包体由 10 MB 变 20 MB），`node:fs.cp` 在 Windows 上重建这些链接则直接 EPERM。据此确定：检出的 `node_modules` 无法被忠实归档，不随包分发；`$DSH_HOME/profiles/node_modules` 同理排除，且它本就是启动时按安装闭包重建的派生状态。
- 处置：新增 `community/portable.mjs`。`check` 报告本机是否具备打包条件；`pack` 暂存并压缩出单个 `tar.gz`，内含完整检出目录与构建产物（`apps/web/dist` 与各包 `lib/`）、已装好插件包的 profile、技能、`start.cmd` 启动器与说明、便携包清单。启动器把 `DSH_HOME` 指向包内 `dsh-home`，并整合出一份「安装链 + 启动」的启动器；`--dry-run` 只报体积，`--with-git` 保留仓库历史。
- 结果：消除打包目标机上的**构建**与**插件重配**两步，保留一次 `pnpm install`（检出的 `node_modules` 无法通过归档搬运）。包体实测 313 MB（x64，不含检出 node_modules）。限同架构使用，原生二进制跨架构会直接崩。
- 验证：本机跑通 `check`、`--dry-run` 与完整 `pack`；归档结构自检确认 `start.cmd`、便携包清单、`repo/apps/web/dist/index.html`、`dsh-home/profiles/web/package.json`、`dsh-home/skills` 均在包内，且不含 `node_modules`。
- 影响范围：`community/portable.mjs`（新增）、`community/README` 双语新增一节并重录配对；未改动 harness 源码与桌面端发布链路。
