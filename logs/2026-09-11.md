## 修复 DeepSeek 请求扩展准备失败（REQUEST_EXTENSION）

- 现象：Web 会话发送任意消息即报「DeepSeek request extension preparation failed」，整轮 DeepSeek 请求被中断。
- 根因：web profile 补丁层插入了主进程插件 @deepseek-ai/dsh-session-import-codex，但该包仅作为若干前端包的 devDependency 存在，未进入 dsh 安装的运行时依赖闭包。开发态由 tsx 的 tsconfig 路径映射兜底完成加载，Loader 条目因此激活；而默认启用的请求扩展包清单插件用 Node 原生解析（createRequire.resolve.paths）逐个校验活动条目所属包，解析不到该包便抛错，导致整轮请求失败。同时 $DSH_HOME/profiles/node_modules 下遗留了指向已消失目标的同名悬空链接。
- 处置：把 @deepseek-ai/dsh-session-import-codex 纳入 apps/cli 的运行时依赖（与同样由 profile 补丁行引用的 dsh-terminal、dsh-terminal-bash 保持一致），执行 pnpm install 生成安装闭包链接；重启 dsh web 后，profile 模块回退目录下的同名链接被自动修复为有效目标。
- 验证：profile 组合中的 162 个裸插件包已全部可被 Node 原生解析（修复前为 161/162）；dsh web 正常启动并输出访问地址。
- 备注：源码与依赖改动需重启 dsh web 后生效。

## 加固模块回退链接的自愈校验（悬空链接）

- 背景：原有自愈判定只核对链接指向是否与解析结果一致，未核对目标是否仍然存在；当某个已声明依赖在磁盘上消失时，其历史遗留的悬空 symlink 会被误判为「已就绪」，从而长期滞留，正是本次故障的残留形态。
- 处置：模块回退目录的「就绪」判定增加悬空检查——属于当前安装闭包已声明但不可解析依赖的悬空 symlink 视为未就绪，在跨进程写锁内清理；仍可解析的链接、未声明的外部链接以及其他 profile 的链接均不在清理范围内。
- 验证：packages/boot/app-boot 的 profile 单测 42 项全部通过（含新增 2 项：悬空链接被清除且不重复生成、已安装依赖的悬空链接被重新指向）。

## 修复桌面壳启动失败只报「等待超时」

- 现象：双击根目录 `DeepSeek Harness.exe` 弹出「timed out after 180s waiting for `dsh web: http...`」，启动页不给出任何真实原因。
- 根因：`dsh web` 在打印就绪地址之前退出时，壳仍走超时分支并固定输出 180 秒文案，丢弃了子进程留在输出管道里的失败信息。本次实测该退出来自 3080 端口已被另一个 `dsh web` 占用（EADDRINUSE）。
- 处置：就绪等待区分「超时」与「子进程提前退出」；失败信息附上子进程退出状态与其输出末尾（含首个 `Error:` 行），不再把提前退出谎报成超时。
- 验证：端口被占用时新壳输出「dsh web exited (exit code 1) before printing `dsh web: http...`」并附 EADDRINUSE 那一行；端口空闲时正常启动并导航到 Web 界面。
- 产物：已重建并更新根目录 `DeepSeek Harness.exe`（壳源码未改启动流程，仅改失败诊断）。

## 修复 0.1.5 插件 RPC 通道无法注册（记忆系统 HTTP 405）

- 现象：升级到 0.1.5 后 dsh-mnemon 记忆系统整体不可用，设置页显示「Mnemom 尚未就绪」，并报两条传输错误 `/dsh-mnemon-read/source-management-catalog: HTTP 405`、`/dsh-mnemon-read/status-summary: HTTP 405`。
- 定位：405 是 dsh-host-frontend-static 的 fallback 语义——只有「非 GET/HEAD 且无命名路由接管」才返回 405，故 RPC 通道从未挂载（POST 落到了只服务静态资源的 fallback）。用探针插件在独立端口实例上复现：`connection.rpc.handle()` 抛 `cannot get property "webServer" without inject`。
- 根因：0.1.2 的 client-connection 插件静态注入 `['webServer', 'credentials']`；0.1.5 重构为动态注入 `ctx.inject(['webServer'], ...)`（仅用于挂载 /api 路由），但 HostConnectionService 内部的 RPC 路由注册仍用 `this.ctx.webServer` 属性访问。该 ctx 已不再持有注入，cordis 因此拒绝属性访问，于是任何调用 `connection.rpc.handle()` 的插件都会失败、其通道永不注册（mnemon 的 handle 调用无 try/catch，异常还中断了它后续的注册代码）。
- 处置：packages/client/connection/src/rpc-host.ts 的 register() 改为先用 `ctx.get('webServer')` 读取全局服务注册表（取不到时抛出明确错误），保持 0.1.5 的注入契约不变。
- 验证：connection host 面类型检查通过；独立端口实例（不带任何补丁）上，mnemon 的 read/activation/write 通道由 405 全部变为 401（已注册、待认证），与宿主 /api 同级；修复前同一实例稳定复现 405。
- 影响面：所有通过 connection 注册 RPC 通道的插件（dsh-mnemon、@dap-dsh-plugins 等），不限于记忆系统。
- 备注：源码改动需重启 dsh web 后生效。

## 运行时记忆启用自动整理

- 背景：MEMORY.md 写入长期贴近上限（10240 字节），此前只能靠手动压缩腾空间；用户询问能否自动整理。
- 定位：自动整理本就内建在 mnemon 框架——写入超限时框架捕获容量错误、读取维护计划，user 目标走本地压缩，memory 目标则把条目归档进一个可写的 Memory Space 再压缩 MEMORY.md；但归档需要至少一个 active 且 remember 能力为真的空间，而本机空间数为 0（记忆系统 405 故障期间留下的状态），于是每次超限都直接以「requires an existing active writable Memory Space」拒绝写入。
- 处置：创建冷归档空间 runtime-memory（id=default，mnemon-native，active、remember=true）。此后单空间场景由框架确定性路由，溢出时自动归档并压缩，无需模型或人工介入。
- 验证：空间目录显示 activeCount=1 且能力齐备；MEMORY.md 当前 8735/10240（余量 1504）。如需更高热容量，可在 profile 的 mnemon-source-runtime 行调 `memoryLimitBytes`（默认 10KB，上限 1MB）。
