# 2026-09-19 开发日志

## 装回 BrowserSkill（浏览器使用）并修复 bsk 运行链路（用户报告）

- 现象：用户要求把 Browser Use 装回来，并提示本机 Edge 里的浏览器扩展应该还在。
- 定位：扩展与 CLI 都还在——Edge 以已解压方式装着 BrowserSkill 0.2.1，`~/.local/bin/bsk.exe`、`~/.bsk` 数据目录齐全；真正缺的是两处：① bsk daemon 完全没有进程与命名管道，`bsk status` 等命令一律挂起；② DSH 的 web profile 里没有任何 BrowserSkill 插件条目。
- daemon 起不来的原因：首次自启时 daemon 发现 0.3.0 新版本，写完 update helper 即退出等待替换；helper 反复替换 `bsk.exe` 失败（日志全是「拒绝访问」，因为 CLI 进程仍占用该文件）。此后若由命令行以子进程方式拉起 daemon，daemon 会随命令超时被一并终止，看起来就像「服务不存在」。
- 处置：改用独立进程启动 daemon，使它脱离命令行进程树；安装官方 DSH 插件 `@wxg-prc-cpg/browser-skill-dsh-plugin@0.2.1`（与 CLI、扩展保持同一版本），由它提供 6 个原生浏览器工具与右栏实时画面；在 web profile 的补丁层补上该插件配置，显式指定 bsk 可执行文件全路径，避免依赖 dsh 启动环境的 PATH。
- 验证：`bsk doctor` 六项全通过（daemon 运行、IPC 正常、协议兼容、Edge 已连接、扩展协议兼容）；实测一次性跑通「开会话 → 打开网页 → 读取页面语义 → 结束会话」，页面标题与链接引用均正常返回。
- 待办：新插件需要重启 dsh web 才会加载；bsk 0.3.0 暂未升级——该版本修了 Windows 升级失败与 daemon IPC，但要求浏览器扩展同步升级，需要用户配合。
- 影响范围：本机 web profile 的 bundle 列表与补丁层（`~/.dsh/profiles/web/package.json`、`cordis.patch.yml`）、本机 bsk daemon 进程；仓库内本次只新增本日志。

## bsk 全套升级到 0.3.0（用户要求）

- 背景：上面记录的升级失败与 daemon 进程识别问题，正是 0.3.0 修掉的两项（Windows 安装/升级失败、daemon 进程身份校验），因此按用户要求把整套升到 0.3.0。
- 处置：CLI 换成官方 release 的 0.3.0 二进制（旧版留备份，并清掉上次失败的升级残留）；扩展按上游的版本目录解压，同时覆盖 Edge 当前加载的那个目录，这样不必改浏览器里的扩展配置；DSH 插件升到同版本 0.3.0；四个 harness 的 skill 用 `--force` 更新到新版（更新前逐个备份，避免误伤自定义内容）。
- 验证：`bsk doctor` 除扩展协议一条外全部通过，daemon 侧新增的进程身份校验也通过；实测跑通「开会话 → 打开网页 → 读取页面语义 → 结束会话」。扩展那条属过渡态：新版文件已在磁盘，而 Edge 仍在跑内存里的旧版本，诊断明确标注「仍可用，建议尽快升级」。
- 待办：Edge 里点一次「重新加载」让扩展真正切到 0.3.0（浏览器内操作不代劳）；插件新版本需重启 dsh web。
- 影响范围：本机 `~/.local/bin`、`~/.local/share/bsk-extension`、四个 harness 的 skill 目录、web profile 的插件依赖版本；仓库内本次只追加本日志。

## 修复桌面壳外链被壳内顶掉 + 把 web profile 固化成可分发版本（用户要求）

- 现象：在桌面壳里点聊天中的 `http://127.0.0.1:8999` 链接，壳没有把它交给系统浏览器，而是自己在 WebView 内导航过去，把 DSH 界面顶掉（需按 Alt+← 退回）。用户同时提出：要把当前这套固化成生产版本——整个目录传到 GitHub 后，另一台机器 clone 下来就能跑出完全一样的插件与功能，且不要再依赖热重载。
- 定位（外链）：壳侧 `is_shell_internal` 用 `Url::host_str()` 判定"壳内地址"，而它**不含端口**，于是 `127.0.0.1:8999` 与本机 harness 被一视同仁。该判定同时守着两条出口（`on_navigation` 同窗口导航与 `handle_new_window` 新窗口请求），所以无论前端拦截器是否生效，本机其它端口都出不去、也不会被拒绝，只能留在壳内。前端侧本已修好（补 `__TAURI_INTERNALS__` 通道），实测运行中的服务确实发的是新版，问题只在壳这一处。
- 定位（可分发）：仓库模板 `community/profiles/web/` 停在 12 个 bundle，而本机 profile 是 17 个——`seed.mjs` 的设计是"只从模板补、绝不删本地多出的"，所以本机手工加的 5 个插件永远回不到模板，新机器自然装不出来。另外 `community/plugins/tarballs/` 里 `ui-layout` 的 tgz 已过期（35794 字节，源头是 38744），与本机实际加载的前端不是同一份。
- 处置（外链）：`external_links.rs` 改为按 origin（含端口）比对，并新增 `remember_harness_origin` 登记 harness 实际地址；`backend.rs::navigate_main` 在导航前登记。随包页面（`tauri.localhost`）与 WebView 内部协议照旧放行。
- 处置（可分发）：模板 bundles 补齐到 17 个并补全依赖；`dsh-desktop-panel` 从 `community/plugins/packages/desktop-panel` 打成 tgz 归入 tarballs，不再依赖开发工具的 junction；把本机补丁层的定制（中文 persona、sandbox/approval、webserver、browser-use、computer-use、desktop-panel、browserskill）合并进模板，并避开机器专属路径。`patchReload` 由 `live` 改为 `startup`，移除补丁层里由 `dev.mjs` 写入的 HMR 托管块——这是"不稳定"的来源。
- 验证：`cargo check` 与 `tauri build` 均通过（release 2m27s，产物 4544000 字节）；用一个全新临时 `DSH_HOME` 跑 `seed.mjs`，生成的 profile 17 个 bundle 全部保留、无插件被丢弃、`patchReload` 为 `startup`、tarball 路径正确指向本 checkout；`ui-layout` 重新打包后内容确认为含 `__TAURI_INTERNALS__` 的新实现，tarballs 与 dist 两处副本 MD5 一致。
- 待办：换掉仓库根的 `DeepSeek Harness.exe` 需要先退出壳（运行中会 EBUSY）；换完由用户在壳里点一次本机其它端口的链接确认走系统浏览器。本机 profile 的 `patchReload` 已手改为 `startup`（seed 不收敛这一项）。
- 影响范围：仓库内 `packages/experimental/web-desktop/src-tauri/src/{external_links,backend}.rs`、`community/profiles/web/{package.json,cordis.patch.yml}`、`community/plugins/tarballs/`（新增 desktop-panel 并更新 ui-layout）、`packages/client/ui-layout/dist/`；本机 `~/.dsh/profiles/web/`（补丁层与清单，已留备份）。
