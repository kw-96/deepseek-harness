## 排查并恢复 web profile 的记忆系统插件 dsh-mnemon

- 背景：用户反馈另一台主机安装过的记忆系统（侧栏「记忆系统」入口）在本机没有加载，询问原因并要求装回。
- 定位：本机该插件并非「装了没启用」，而是 2026-09-13 17:00 web profile 清单整体重写时未被写回——`package.json` 的 `dsh.profile.bundles`、`dependencies`、`cordis.patch.yml`、profile `node_modules` 四处均无 dsh-mnemon；`cordis.patch.yml` 自 09-12 起未再改动，说明不是显式卸载或禁用（那会留下 disabled 行）。同 09-07、09-11 两次历史记录一致：该插件曾被同类重写移除过一次。
- 处置：安装外部 `mnemon` 二进制（npm 全局，版本 0.2.8，与本机 DSH 0.1.5-rc.1 的兼容基线一致）；把`dsh-mnemon` 0.5.8 装入 web profile，并在 bundle 层与依赖中登记；确认插件自带的 cordis 补丁层已包含 0.1.5 所需的 connection RPC 注册修复。
- 已知阻塞：profile 依赖安装未能跑完 —— 本机非管理员无法创建符号链接，pnpm 在重导入链接包（`dsh-codex-shell` 的 `@testing-library/react`）时稳定报 `ERR_PNPM_EPERM`；运行时文件与其依赖闭包均已落盘、模块解析预检全部通过，但依赖图状态未收尾。
- 影响面：凡需要重新导入工作区链接包的 profile 安装/更新都会撞上同一限制，不限于记忆系统。
- 验证（宿主重启后）：Mnemon 的运行时记忆段已随系统提示注入会话，`mnemon_status` 报 healthy、`commandFound` 与 `writeEnabled` 均为真；记忆空间数为 0 的旧状态已修复——新建并激活冷归档空间 `runtime-memory`（id `default`，mnemon-native），此后热容量触顶会自动归档再压缩；profile 清单在重启后仍保留 dsh-mnemon 登记。

## 复核：开发者模式未能免除符号链接提权

- 现象：用户开启 Windows 开发者模式并重启后，非提权进程创建符号链接仍被拒（「此操作需要管理员权限」），在任何目录都不成立。
- 定位：注册表 `AppModelUnlock\AllowDevelopmentWithoutDevLicense` 已为 1、无组策略覆盖，但当前账户的管理员组身份是**经过 UAC 过滤的令牌**（`IsInRole(Administrator)` 为假），策略未对该令牌放行创建符号链接的权限。
- 结论：开发者模式在本机不是「重启即生效」的解法；收尾 profile 依赖图需在提权终端补跑一次安装，以 UAC 提示作为授权入口，不需要再次重启。
- 收尾（已闭环）：用户在管理员终端补跑 profile 安装成功（`Packages: +24 -12, added 24, done`），随后复跑安装返回 `Already up to date`，此前报 EPERM 的 `codex-shell` 链接目标已就位；记忆系统的 bundle 登记与运行时模块解析在安装后再次复检通过。此前的未完成状态仅为链接补齐，不涉及宿主代码，因此无需再次重启。

## dsh-desktop（Electron）可行性实验：能否替代现有独立窗口

- 背景：评估用仓库内的 Electron 桌面端替代现有 Tauri 独立窗口（根目录 `DeepSeek Harness.exe`）的可行性；要求全程不扰动正在运行的实例，只做验证不做迁移。
- 处置：
  - 实验全程使用隔离 home 与一次性桌面 profile，真实 `DSH_HOME` 只读访问；未执行仓库构建，未改动前端产物与客户端 bundle，未触碰运行中的服务与窗口进程。
  - 补齐 Electron 运行时二进制，并准备可复用的实验脚本：隔离 profile 准备、桌面宿主直驱、窗口启动与渲染进程取证。
  - 桌面 profile 按官方开发路径的链接布局搭建，社区插件包以复制方式进入实验项目，用于验证桌面组合能否挂载现有插件集合。
- 验证：
  - 基线组合（base + web-app）启动成功，桌面协议返回页面 200，说明 Electron 路线在本机可运行。
  - 只加入社区插件 bundle 而不带 profile 补丁层时，`dsh-codex-shell` 因缺少 terminals 服务停在 pending；补入现有 web profile 的补丁层后组合完整就绪。
  - 真实窗口渲染成功，页面文案来自社区插件 `dsh-codex-left` 的客户端字典，证明插件的客户端半边在 Electron 窗口中确实挂载；插件客户端包经桌面协议可取（HTTP 200）。
  - 桌面端窗口使用系统装饰与自身原生菜单，Tauri 专用自绘顶栏在 Electron 下不生效；外链在 Electron 下没有出口（新窗口请求被拒且无系统浏览器转交）。
- 影响范围：仅新增 `.artifacts/desktop-probe` 下的实验产物，以及依赖目录中的 Electron 二进制；产品代码、配置与 profile 均未改动。真实 `DSH_HOME` 与运行中的实例未受影响（实验期间该 profile 自身有一次插件安装活动，即上一条记录，与本实验无关）。

## 播种机制改为向模板收敛，免去新主机手工装插件

- 背景：另一台主机上已有 profile 时，播种只修正 tarball 路径与丢弃装不上的组合包，不会补上模板新增的插件，用户需手工执行安装命令；目标是拉取后直接启动即可获得同一套插件。
- 处置：把"修护"扩展为"收敛"——按模板补齐缺失的组合包、依赖与 `allowBuilds` 条目，按新增的 `retired.json` 下线被取代的组合包并清理其失效补丁行；模板之外由用户自行添加的内容仍然保留。
- 补漏：`pnpm dsh` 一直会先跑播种，但桌面壳与双击启动走的 `dsh.cmd` 不会，导致那条启动路径仍然要手工装插件；已把播种加入 `dsh.cmd`，失败时只告警并继续启动。
- 验证：以改动前的 profile 快照做仿真，一次运行即收敛到与本机一致的 17 个组合包（含六个新插件、无 codex 残留、构建白名单就位、失效补丁行清除），第二次运行无任何变更（幂等）；全新主机播种路径与真实 profile 自检均不受影响。
- 影响范围：`community/seed.mjs`、`community/profile.mjs`、`community/profiles/web/retired.json` 与社区双语文档；插件与运行时行为不变。

## 修复播种收敛把 tarball 占位符写进 profile 清单（会导致下次启动直接起不来）

- 背景：拉取 dev 最新版后准备重启本机实例，先核对本机 web profile 与新版模板的差异。
- 定位：模板把社区 tarball 依赖写成占位符，只有首次播种会替换它成真实路径；已有 profile 的收敛路径直接照抄模板原样写进清单，依赖指向一个任何主机都不存在的目录。依赖安装随即以「找不到文件」中止，新组合包一个都没落盘，而组合列表里已经写上了它们——重启时加载器解析不到就拒绝启动，属于「装完插件、下次启动才炸」的典型形态。
- 处置：收敛路径与首次播种共用同一套占位符解析；已经写入占位符的清单在下次收敛时也能被纠正回来。
- 验证：在隔离 DSH_HOME 上以本机 profile 快照复现——修复前依赖安装立即中止且无任何包落盘，修复后 505 个包安装成功（含 node-pty 预编译二进制，耗时 1 分 20 秒）；随后组合自检 21 个组合包、172 条插入行、插入行 id 无重复，主机自检报「profile 配置与当前仓库一致」，即收敛幂等。
- 影响范围：`community/profile.mjs`；本机 web profile 尚未收敛，重启时由播种完成。
